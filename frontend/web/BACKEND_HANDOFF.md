# Что нужно backend для полного интерфейса Aivritm

## Реализовано в текущем прототипе 31 октября 2026

Добавлены рабочие пространства текущего локального профиля: `GET/POST /api/workspaces`,
`PATCH /api/workspaces/{id}`. В БД миграция v3 добавляет `workspaces` и
`events.workspace_id` с default=1 для существующих данных. Старые ID, история
и цвета сохраняются. Новые пространства изначально пустые.

`POST /api/events`, `POST /api/message` принимают `workspace_id` в JSON.
Список событий, поиск, история, PATCH/DELETE записи и её цвет принимают
`workspace_id` в query. Без него используется обычное «Общее пространство»
с ID=1. История и pending-подтверждения AI разделены по пространствам;
request_id нельзя повторно использовать в другом пространстве.
Активное пространство восстанавливается из localStorage, профиль/цветовые
настройки остаются общими. Операции удаления пространства не добавлялись.

Важно: в реальном Python/SQLite-прототипе ещё **нет авторизации и user_id**,
в отличие от предложенной ниже ER-схемы. Это пространства одного локального
профиля, а не изоляция нескольких авторизованных пользователей. При переносе
на backend с users нужно связать workspace с владельцем и проверять его
во всех запросах. Подробности: [WORKSPACES_REPORT.md](WORKSPACES_REPORT.md).
Остальная часть документа описывает требования к полноценному backend.

Документ для передачи backend-разработчику. Дата: 30 октября 2026 года.

Основание: предоставленная ER-схема (`users`, `sessions`, `planner_items`,
`item_types`, `item_statuses`) и текущий интерфейс задач, встреч, напоминаний
и ассистента. Ниже разделены уже предусмотренные данные, недостающие возможности
и необходимые методы API. Предлагаемые названия новых полей и маршрутов
нужно согласовать; они не означают, что эти методы уже реализованы.

## 1. Что в схеме уже есть

Схема покрывает основу продукта:

- Пользователь, логин, email, часовой пояс и авторизационные сессии.
- Запись с владельцем, типом, статусом, названием и описанием.
- Начало и окончание: `start_at`, `end_at`.
- Срок без времени: `due_on`; точный срок: `due_at`.
- Одно время напоминания: `remind_at`.
- Даты создания и обновления.

Описание и раздельные временные поля добавлять в БД повторно не требуется.
Их нужно предоставить через API и определить правила использования.
Справочник статусов есть, но конкретные значения на рисунке не указаны:
наличие состояния «В процессе» нужно подтвердить seed-данными.

## 2. Чего не хватает и зачем это интерфейсу

| Возможность | Что требуется | Обоснование |
| --- | --- | --- |
| Приоритет задачи | Отдельное `priority`, например `urgent`, `important`, `medium`, `low`; определить значение «не задан» | В интерфейсе есть срочность, цветовые обозначения и сортировка. По статусу или пользовательскому цвету приоритет определить нельзя |
| «В процессе» | Стабильный код статуса, например `in_progress`, и допустимые переходы | Нужны группы «Созданные / В процессе / Завершённые» и изменение статуса в редакторе |
| Время завершения | `completed_at`, устанавливаемое сервером | Подпись «Выполнено в 09:20» должна показывать завершение. `updated_at` может измениться после переименования и для этого не подходит |
| Индивидуальный цвет | Nullable `color` записи или отдельное хранилище по ID | Пользователь меняет цвет конкретной записи; он должен сохраняться после перезагрузки и на другом устройстве |
| Цвет типа пользователя | Настройки по `(user_id, item_type_code)` | Изменение стандартного цвета встреч должно затрагивать все встречи без индивидуального цвета, но не настройки другого пользователя |
| Пространства | `workspaces` и связь записи через `workspace_id`; права при совместном использовании | Верхний селектор должен переключать набор записей и поиск. `user_id` обозначает владельца и не заменяет пространство |
| Рабочие календари | `calendars` и связь `calendar_id`, если выбор календаря включён в поставку | Чтобы выбор календаря при размещении записи действительно менял принадлежность и отображение |
| Настройки напоминания | Включение/отключение, абсолютное время либо относительное смещение и базовый момент | Для действия «за 10 минут» нужно знать намерение пользователя и пересчитывать отправку при переносе события |
| Доставка напоминания | Фоновая обработка, состояние отправки, ошибки и повторы | Наличие `remind_at` не отправляет уведомление. Отправка должна работать при закрытой странице и после перезапуска сервера |
| Центр уведомлений | Записи уведомлений, состояние прочтения и доставки | Иконка уведомлений и число непрочитанных должны соответствовать реальным данным |
| История ассистента | Разговоры, сообщения, ожидаемые предложения и результаты исполнения | После перезагрузки должны восстанавливаться переписка и доступные действия подтверждения/отказа |
| Мягкое удаление | `deleted_at` либо согласованный эквивалент | Текущий API уже использует мягкое удаление; при переходе на новую схему это поведение нужно сохранить |
| Одновременное редактирование | Версия или ETag и проверка условия при PATCH | Два открытых клиента не должны молча перезаписывать изменения друг друга. Один `updated_at` без такой проверки этого не обеспечивает |

Для цветов действует порядок: **индивидуальный цвет → цвет типа пользователя →
системный цвет**. Null у индивидуального цвета означает наследование.
Приоритет и персональная окраска хранятся и отображаются независимо.

При возврате завершённой задачи в открытые нужно согласовать поведение
`completed_at`; предлагается очищать его, а историю изменений хранить отдельно.

## 3. Важные правила времени и напоминаний

`due_on` — дата без времени: её нельзя превращать в полночь UTC и затем
сдвигать по часовому поясу. `due_at`, `start_at`, `end_at`, `remind_at` —
моменты времени; API должен отдавать их со смещением либо в UTC.
`users.timezone` определяет зону отображения по умолчанию.

Дедлайн и размещение в календаре — разные значения. Например, задачу можно
выполнять с 13:30 до 14:00, иметь срок в 18:00 и напоминание в 17:50.
Одно поле даты не передаёт этот сценарий. Ограничение схемы, запрещающее
одновременно заполнять `due_on` и `due_at`, нужно сохранить в API-валидации.

Для одного абсолютного напоминания `remind_at` достаточно как поля времени.
Можно начать с настройки через POST/PATCH записи без отдельной таблицы
напоминаний. Для относительного варианта нужны режим, смещение и привязка
к началу встречи или сроку задачи. Например, перенос встречи с 15:00 на 16:00
должен сдвигать напоминание «за 10 минут» с 14:50 на 15:50.

Если нужны несколько напоминаний или разные каналы, настройки следует вынести
в связанную сущность. В любом варианте сервер должен отменять ожидающую отправку
при отключении/удалении, обрабатывать временные ошибки и предотвращать повторную
отправку одной операции. Канал доставки для первой версии нужно выбрать явно.

## 4. Какие методы API нужны

Использовать фактические маршруты backend, если они уже определены.
Ниже — ожидаемые возможности и предлагаемые названия.

| Метод / область | Назначение |
| --- | --- |
| Вход/выход, например `POST /api/auth/login`, `POST /api/auth/logout` | Создание и завершение авторизационной сессии; регистрация — если предусмотрена продуктом |
| `GET /api/me`, `PATCH /api/me` | Получение профиля, изменение разрешённых полей и часового пояса |
| `GET /api/item-types`, `GET /api/item-statuses?item_type_code=task` | Коды, названия и допустимые статусы по типу; переходы должны быть определены контрактом |
| `GET /api/events` | Список с фильтрами, серверной сортировкой, пагинацией и полными счётчиками групп |
| `GET /api/events/{id}` | Получение актуальной записи для редактора, поиска, ссылки или уведомления |
| `POST /api/events` | Создание с описанием, приоритетом, временными полями, цветом и связями при их наличии |
| `PATCH /api/events/{id}` | Изменение всех разрешённых полей, проверка версии, возврат актуальной записи |
| `DELETE /api/events/{id}` | Согласованное мягкое удаление и отмена ожидающих напоминаний |
| `GET /api/search` | Поиск с учётом пользователя, выбранного пространства и других доступных фильтров |
| `GET /api/colors` | Цвета типов текущего пользователя и индивидуальные цвета доступных записей |
| `PATCH /api/colors/defaults/{event_type}` | Сохранение стандартного цвета типа или сброс |
| `PATCH /api/events/{id}/color` | Индивидуальный цвет или возврат к наследованию |
| `GET /api/workspaces` и управление пространствами | Заполнение верхнего селектора и работа с пространствами |
| `GET /api/calendars` и управление календарями | Заполнение выбора календаря, если он входит в поставку |
| Настройка напоминания через запись либо отдельный CRUD | Для одного напоминания достаточно полей записи; для нескольких — например `GET/POST /api/events/{id}/reminders`, `PATCH/DELETE /api/reminders/{id}` |
| `GET /api/notifications`, `PATCH /api/notifications/{id}` | Центр уведомлений, пагинация, непрочитанные и отметка прочтения |
| `POST /api/message`, `GET /api/history` | Диалог, уточнения, подтверждение/отказ и восстановление состояния |

В текущем приложении уже работают список/создание/PATCH/DELETE записей, поиск,
цвета, сообщения и история. Их нужно расширить и связать с новой моделью и
владельцем, сохранив совместимость. Отдельный дублирующий CRUD `/tasks` не нужен:
задачи, встречи и напоминания уже представлены через `/events`.

Создание в чате уже поддерживает `require_confirmation: true`, предложение
до записи в БД и подтверждение/отказ через «Да»/«Нет» в `/api/message`.
Повтор использует прежний `request_id` и не должен создавать дубликат.
Отдельные `/confirm` и `/reject` для этого существующего сценария не обязательны.

## 5. Что согласовать в контракте до подключения

- **Имена и состав DTO.** Сейчас frontend ожидает `type`, `status`, `date`,
  `time`, `duration_min`, `is_deadline`, `source`, `source_ref`, `deleted_at`.
  Строку `planner_items` нельзя отдать вместо этого DTO без адаптера или
  одновременного обновления frontend. Происхождение архивных записей нужно сохранить.
- **Статусы.** Нужны коды и переходы, а не только числовой `status_id`.
  Текущий клиент принимает `planned/done`; новый `in_progress` подключается согласованно.
- **Идентификаторы.** Для полного диапазона `bigint` следует согласовать строковые
  ID в JSON; текущий frontend использует числа и потребует соответствующей правки.
- **PATCH.** Отсутствующее поле означает «не менять», null — «очистить», если
  очистка разрешена. Ответ должен содержать актуальную запись; конфликт версии —
  явную согласованную ошибку.
- **Даты.** Определить зону фильтра «Сегодня», поведение пустого `end_at` и
  миграцию старых дат/времени без timezone. Просто дописать `Z` к ним нельзя.
- **Пользователь и диалог.** Авторизационные `sessions` из схемы и текущая
  сессия ассистента имеют разные назначения. Разговору нужен отдельный ID;
  доступ к записям проверяется по вошедшему пользователю, а не по ID разговора.
- **Выдача списка.** Зафиксировать фильтры, стабильную сортировку, пагинацию и
  счётчики по всему отфильтрованному набору. Это нужно для большого архива.
- **Миграция.** Сохранить существующие записи, цвета, историю и происхождение
  данных; проверки миграции выполнять на копии/временной базе.

## 6. Очерёдность и критерии готовности

Первая поставка: согласованный DTO и авторизация, описание/приоритет/статусы,
временная модель, завершение, цвета пользователя и работающий механизм напоминаний.
Пространства и календари включить в эту поставку, если соответствующие селекторы
должны работать сразу. Совместное использование, файлы и внешняя синхронизация
могут поставляться отдельно после определения их контрактов.

Поставка готова к подключению, когда:

1. Задача создаётся и редактируется со всеми согласованными полями, повтор не создаёт дубль.
2. Переходы статусов и время завершения одинаково видны в списке, редакторе и «Моём дне».
3. Цвет типа наследуется, индивидуальный цвет имеет приоритет, сброс возвращает наследование.
4. Дедлайн, календарный интервал и напоминание сохраняются независимо и корректно отображаются в timezone пользователя.
5. Перенос, отключение и удаление корректно меняют ожидающую отправку напоминания; закрытие страницы не останавливает отправку.
6. Чат сохраняет предложение до подтверждения, отказ ничего не создаёт, перезагрузка и повторы не исполняют действие дважды.
7. Смена пользователя/пространства не смешивает чужие данные, а конфликт редактирования явно обрабатывается.

Для начала интеграции нужны **фактическая OpenAPI**, значения справочников,
примеры ответов для задачи/встречи/напоминания, правила ошибок и null,
способ авторизации и согласованный план совместимости. ER-схема описывает
хранение, но сама по себе не определяет этот HTTP-контракт.
