# Персонализация цветов Aivritm

Обновление: цвета задач теперь заметны и в мягкой подложке карточек;
цвет можно выбрать в отдельной форме создания. Последний прогон —
470 pytest / 15 unit / 46 Playwright. Подробности в [FIXES.md](FIXES.md).

## Реализованное поведение

Верхняя кнопка **«Цвета»** открывает настройки стандартных цветов задач,
встреч и напоминаний. В редакторе каждой записи доступен **«Цветовой акцент»**.
В форме сообщения ассистенту есть выбор **«Цвет новой записи»**: он применяется
при создании, в том числе после уточняющего вопроса. Существующий диалоговый
workflow создания, конфликтов и подтверждений сохранён.

Приоритет цвета: индивидуальное переопределение → настройка типа → системный цвет.
При смене цвета типа обновляются все наследующие записи; индивидуальные цвета
не меняются. «Использовать цвет по умолчанию» удаляет переопределение после
нажатия «Применить цвет». Выбор того же HEX вручную остаётся явным переопределением.
При создании без индивидуального цвета в metadata не копируется цвет типа.

Предпросмотр не меняет сохранённые данные. Объект получает новый акцент только
после подтверждения backend. Ошибка оставляет предыдущий цвет и выбранный
черновик; можно повторить сохранение. Цвет редактора сохраняется отдельно от
названия/даты/статуса и не отправляет родительскую форму.

Акценты применяются к задачам, встречам в «Мой день», записям календаря,
напоминаниям, редактору и карточкам диалога. Для напоминаний вычисляется мягкая
подложка. Цвет текста остаётся системным; для отметок выбранного образца
выбирается чёрный или белый текст по контрасту. Цвета опасных действий и
семантические токены приоритетов не изменяются.

## Архитектура и сохранение

Frontend остаётся статическим ES-модульным приложением. Миграция на React/Next.js
в эту функцию не входит. Новые модули проверяются TypeScript strict/checkJs:

- `lib/colors.js`: HEX, наследование, мягкие подложки, контраст и серверное состояние.
- `lib/color-picker.js`: переиспользуемая палитра, native color input, HEX и popover.
- `lib/color-settings.js`: настройки типов и цвет следующей создаваемой записи.
- `lib/views.js`, `lib/editor.js`, `app.js`: единое применение акцентов.

Backend использует существующую таблицу SQLite `metadata`:

| Ключ | Значение |
| --- | --- |
| `appearance.default.task` / `meeting` / `reminder` | Пользовательский HEX; отсутствие ключа означает системный цвет |
| `appearance.event.<id>` | Только явное индивидуальное переопределение |
| `appearance.request.<request_id>` | Значение цвета запроса для проверки идемпотентности |

Новая таблица и миграция схемы не нужны. `ritm/contracts.py`, схема Event,
перечисления статусов/типов и существующие ответы `/api/events` не изменены.
При мягком удалении запись не попадает в выдачу цветов. Перезапуск backend
не сбрасывает настройки. Создание записи, цвет и регистрация запроса коммитятся
в одной транзакции; при ошибке сохранения цвета создание откатывается целиком.

localStorage не используется для хранения стандартных или индивидуальных цветов.
sessionStorage содержит только существующий черновик повторяемого запроса с его
цветом: это позволяет повторить тот же запрос после потери ответа без дубля.
Данные сохраняются на сервере; подключение внешнего облака не заявляется.

## Реальные HTTP-методы

### `GET /api/colors`

```json
{
  "defaults": { "task": "#4f72d8", "meeting": null, "reminder": null },
  "overrides": { "42": "#ff8800" }
}
```

`null` в defaults означает системный цвет. Отсутствие ID в overrides означает
наследование. Эффективные цвета не записываются обратно как переопределения.

### `PATCH /api/colors/defaults/{event_type}`

Тип: `task`, `meeting` или `reminder`.

```json
{ "color": "#4f72d8" }
```

Ответ: `{"type":"task","color":"#4f72d8"}`.
`{"color":null}` возвращает системный стандарт этого типа.

### `PATCH /api/events/{event_id}/color`

```json
{ "color": "#ff8800" }
```

Ответ: `{"event_id":42,"color":"#ff8800"}`.
`{"color":null}` удаляет индивидуальную настройку.
Для отсутствующей или удалённой записи — 404. Бизнес-поля Event не меняются.

### Дополнение `POST /api/message`

Необязательное поле `new_event_color` — HEX или `null`; старые запросы остаются
валидными без этого поля. При `kind=created` цвет применяется к созданной записи.
При `duplicate`, поиске, переносе и других действиях существующая запись
не перекрашивается. На уточняющих шагах frontend передаёт выбранный цвет снова.

Повтор прежнего `request_id` с другим цветом возвращает 409, как и повтор
с другим текстом. Тот же запрос возвращает сохранённый ответ и не применяет
цвет заново поверх последующих изменений пользователя.

Backend принимает только `#RRGGBB`, нормализует регистр, отклоняет прочие
CSS-значения с 422. UI также принимает короткий `#RGB`, разворачивая его перед
отправкой. Лишние поля и запрос без обязательного `color` отклоняются.

для ручного тестирования. Артефакты: `%TEMP%\aivritm-colors-qa\`:
`colors-calendar-and-chat.png`, `colors-reminder-editor.png`, `colors-save-error.png`,

## Ограничения и решения для Claude

1. У приложения нет авторизованных пользователей. Настройки принадлежат общему
   локальному профилю сервера. Разделение между пользователями потребует владельца
   настроек и серверной проверки доступа после появления авторизации.
2. Отдельного типа «событие календаря», пользовательских категорий и пространств
   в контракте нет. Календарь показывает цвета трёх существующих типов.
3. В Event нет приоритета. Его enum и поля не добавлялись в обход владельца
   контракта. Проверены неизменность семантических токенов и бизнес-полей, но
   сквозной сценарий «синяя срочная задача с красным badge» заблокирован до
   появления приоритета в backend. Текстовая метка срочности не выдумывалась.
4. Незавершённый выбор цвета — черновик. Постоянные настройки типов и сохранённые
   переопределения переживают перезагрузку; создание по-прежнему идёт через диалог.
5. Цвета перечитываются после операций и по фокусу окна. Мгновенная синхронизация
   между устройствами, ETag и отдельная политика конфликтов настроек пока отсутствуют.

Владельцу общего контракта нужно учесть реализованный DTO цветов при дальнейшем
версионировании API и согласовать привязку к будущим пользователям/пространствам.
