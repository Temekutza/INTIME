# Aivritm — что требуется от backend для полного интерфейса

Дата: 30 октября 2026 года.

Обновление 31 октября: `require_confirmation: true` теперь также откладывает
перенос даты/времени до согласия пользователя. Добавлена явная команда
`Переименуй задачу «Старое название» в «Новое название»` (также встречу/напоминание):
выбор при неоднозначности, preview, отказ/подтверждение и replay по request_id.
Новые endpoints и изменения общих Event/ParsedCommand для этого не потребовались.
Удаление уже доступно в редакторе всех трёх типов. См. `MASTER_FIX_REPORT.md`.

Документ для backend-разработчика. Основан на текущих `ritm/api/app.py`,
`ritm/contracts.py` v1.3 и реализованном frontend в `web/`.
Описанные ниже новые маршруты и поля — предложения для согласования,
а не уже существующий API. Общий контракт проекта согласует Claude.

## Сверка с присланной схемой БД

Схема содержит `users`, авторизационные `sessions`, `planner_items`, `item_types`
и `item_statuses`. Ниже оценивается именно представленная схема: наличие таблицы
не подтверждает наличие работающего HTTP API. Текущий frontend пока использует
DTO `RitmEvent` из `web/lib/types.d.ts`, а не строки `planner_items` напрямую.

### Что схема уже покрывает

| Требование интерфейса | На схеме | Что ещё нужно для подключения |
| --- | --- | --- |
| Пользователь и его timezone | `users.id/login/email/timezone` | Авторизация, `GET/PATCH /api/me`, проверка владельца на сервере |
| Авторизационные сессии | `sessions.user_id/token_hash/expires_at` | Методы входа/выхода и согласованный способ передачи сессии |
| Задача, встреча, напоминание | `planner_items.item_type_code` → `item_types.code` | Зафиксированные коды `task/meeting/reminder` в DTO и OpenAPI |
| Название и описание | `title`, nullable `description` | Отдавать и принимать описание в API создания/редактирования |
| Статусы по типам | `status_id` → `item_statuses`, связь по типу и ID | Seed-значения, коды статусов и переходы; на рисунке самих значений нет |
| Начало и окончание | `start_at`, `end_at` | Семантика встречи и размещения задачи в календаре; оба момента в ответах API |
| Срок задачи без времени | `due_on: date` | Возвращать как календарную дату, без конвертации через UTC |
| Точный срок задачи | `due_at: timestamptz` | Возвращать ISO 8601 с UTC/смещением; вместе с `due_on` не заполнять |
| Одно время напоминания | `remind_at: timestamptz` | Настройка/отмена и фоновая доставка, описанные ниже |
| Даты создания/изменения | `created_at`, `updated_at` | Включить в DTO; для конфликтов редактирования нужен дополнительный протокол |

Схема уже содержит описание и раздельные временные поля: добавлять их в БД
повторно не требуется. В запущенном API эти возможности ещё не представлены
полностью. `user_id` определяет владельца и не заменяет рабочее пространство.

### Чего ещё нет для интерфейса из референсов

| Недостающая возможность | Минимальное дополнение / согласование |
| --- | --- |
| Срочная / важная / средняя / низкая | Отдельное поле `priority` со стабильными кодами, например `urgent/important/medium/low`; отсутствие приоритета определить явно |
| «В процессе» | Убедиться, что соответствующий статус есть в seed-данных `item_statuses`; одной структуры справочника недостаточно |
| Фактическое завершение | `completed_at: timestamptz`, серверная установка при завершении и согласованное поведение при возврате в открытые |
| Индивидуальная окраска | Nullable `color` у записи или отдельное хранилище по ID записи; null означает наследование |
| Цвета типов пользователя | Настройки по `(user_id, item_type_code)` с HEX-цветом; текущие локальные цвета нужно перенести с согласованным владельцем |
| Селектор пространства | `workspaces`, принадлежность записей через `workspace_id`, доступы при совместном использовании |
| Выбор рабочего календаря | `calendars` и связь `calendar_id`, если этот выбор входит в первую поставку |
| «За 10 минут», вкл./выкл., состояние доставки | Режим абсолютного/относительного напоминания, offset, enabled и данные фоновой отправки; один `remind_at` этого не описывает |
| Центр уведомлений | Отдельные данные уведомления, прочтения и доставки |
| Мягкое удаление записи | `deleted_at` либо согласованный эквивалент; у текущего API удаление мягкое |
| Защита одновременного редактирования | Версия / ETag и условие в PATCH; наличие `updated_at` без проверки условия не предотвращает перезапись |
| История и предложения ассистента | Разговоры, сообщения, ожидаемые подтверждения и идемпотентные запросы; на присланной схеме этих данных нет |

Файлы, общий доступ и внешняя синхронизация на схеме также не представлены;
это следующие этапы, если функции остаются в продукте.

### Напоминания: что можно сделать без лишнего расширения

Для MVP с одним абсолютным напоминанием на запись `remind_at` может быть
достаточно как поля времени. Необязательно сразу вводить несколько напоминаний
и отдельный CRUD `/reminders`: настройку можно передавать в POST/PATCH записи.
Но backend всё равно должен выполнять отправку, переживать перезапуск и
различать ожидающую, отменённую, отправленную и неудачную доставку.

Для показанного UI «напомнить за 10 минут», переключателя и переноса встречи
нужно хранить намерение пользователя: абсолютное время либо смещение относительно
`start_at`/`due_at`. Иначе нельзя однозначно решить, переносить ли `remind_at`
вместе со встречей. Если нужны несколько напоминаний или разные каналы,
настройки следует вынести в связанную сущность; методы ниже описывают этот вариант.

### Какие методы и ответы нужны frontend

Названия новых маршрутов ниже — предложение. Если backend уже использует другие,
нужны его фактические OpenAPI и примеры; дублировать работающие методы не нужно.

| Область | Требуемый API |
| --- | --- |
| Авторизация | Вход/выход, например `POST /api/auth/login`, `POST /api/auth/logout`; регистрация — если предусмотрена продуктом |
| Профиль | `GET/PATCH /api/me`: ID, отображаемое имя/логин, timezone; без `password_hash` и `token_hash` |
| Справочники | Например `GET /api/item-types`, `GET /api/item-statuses?item_type_code=task`; стабильные коды и допустимые переходы |
| Записи | Сохранить и расширить `GET/POST /api/events`, `GET/PATCH/DELETE /api/events/{id}`; GET по ID пока отсутствует |
| Список и поиск | Период, тип, статус, приоритет, пространство/календарь при их наличии; сортировка, пагинация, полные счётчики |
| Цвета | Существующие `GET /api/colors`, `PATCH /api/colors/defaults/{event_type}`, `PATCH /api/events/{id}/color`, но в контексте вошедшего пользователя |
| Ассистент | Сохранить `/api/message` и `/api/history`, подтверждение/отказ и защиту от повторного исполнения; связать диалог с владельцем |
| Пространства/календари | Методы получения списка и управления, если соответствующие селекторы должны работать |
| Напоминания/уведомления | Настройка в записи для одного напоминания либо отдельный CRUD; список уведомлений и отметка прочтения при наличии центра |

Авторизационные `sessions` на схеме и текущий `session_id` ассистента имеют разные
назначения. Диалогу нужен отдельный идентификатор, например `conversation_id`;
идентификатор разговора не должен давать доступ к чужим данным. Хранилища
авторизации и диалога нельзя объединять только из-за совпадающего имени `sessions`.

### Сопоставление с текущим контрактом frontend

| Сейчас frontend ожидает | В новой модели | Что согласовать |
| --- | --- | --- |
| `id: number` | `bigint identity` | Допустимый диапазон JSON ID; для полного bigint использовать строку и одновременно изменить frontend DTO/хранилище |
| `type` | `item_type_code` | Сохранить наружное имя `type` либо выпустить согласованный адаптер |
| `status: planned/done` | `status_id` + справочник | Отдавать стабильный код; расширение на `in_progress` внедрить одновременно с frontend |
| `date`, `time`, `is_deadline` | `due_on`/`due_at`, `start_at`, `remind_at` | Выбирать поля по смыслу объекта; нельзя свернуть дедлайн и календарный интервал в одну дату |
| `duration_min` | `start_at`, `end_at` | Семантика nullable окончания, вычисление длительности и сохранение при переносе |
| `source`, `source_ref` | На схеме отсутствуют | Сохранить происхождение пользовательских/архивных записей либо согласованно изменить DTO и миграцию |
| `deleted_at` | На схеме отсутствует | Сохранить мягкое удаление и фильтрацию удалённых записей |

Текущий строгий валидатор не примет строку БД вместо `RitmEvent`: переименование
полей, новые статусы, строковые ID и отсутствие обязательных старых полей требуют
совместимого DTO либо согласованного обновления клиента. Пустой `end_at` допустим
по схеме; frontend не должен придумывать окончание или длительность такой встречи.

`timestamptz` задаёт момент времени, а `users.timezone` — зону отображения по
умолчанию. В API нужны значения со смещением/UTC; дату `due_on` отображлять как
дату. Нужно определить, в какой зоне фильтр «Сегодня» вычисляет границы суток,
и сохранить смысл старых naive `date/time` при миграции.

**Следующая поставка от backend:** фактическая OpenAPI, значения справочников,
примеры ответа для трёх типов и всех статусов, правила null/ошибок, схема
авторизации и план совместимости. Затем можно подключать новые поля frontend;
по одной ER-схеме изменять рабочий API-клиент преждевременно.

### Обновление: персонализация цветов реализована

Добавлены реальные методы `GET /api/colors`,
`PATCH /api/colors/defaults/{event_type}`, `PATCH /api/events/{id}/color`
и необязательное поле `new_event_color` в `POST /api/message`.
Они используют существующую таблицу `metadata` в SQLite; схема Event и бизнес-поля
не менялись. Действуют для общего локального профиля, типов task/meeting/reminder.
Это выполненная часть, а не требование реализовать её повторно.
Контракт цветов и проверки описаны отдельно в `web/COLORS.md`.
После появления пользователей потребуется привязать настройки и доступ к владельцу;
после появления новых типов/пространств — согласованно расширить доступные цвета.

### Обновление: базовая форма создания реализована

Добавлен реальный `POST /api/events`: название, тип, дата/время, длительность
встречи, признак дедлайна и цвет. Использует существующий core, идемпотентность
и подтверждения конфликтов/прошедшей даты. Ответ — envelope ассистента с HTTP 200.
Это выполненная часть. Описание, приоритет, пространство и календарные связи
по-прежнему требуют согласования. DTO и проверки приведены в `web/FIXES.md`.

### Обновление: подтверждение создания в чате реализовано

`POST /api/message` принимает необязательное `require_confirmation: true`.
Web-клиент передаёт его во всех сообщениях: после уточнений сервер возвращает
`kind: "confirm"`, `expecting: "confirmation"`, `proposal` с названием, типом,
датой/временем, длительностью, признаком дедлайна, intent и цветом.
До «Подтвердить» запись отсутствует в `/api/events`.
Подтверждение/отказ идут тем же методом, с текстом `Да`/`Нет`, прежним
`session_id` и новым уникальным `request_id`. Повтор использует прежний ID.
Новые отдельные `/confirm` и `/reject` сейчас не требуются.

`GET /api/history` дополнительно возвращает `request_id` сообщений,
`proposal`, `active_confirmation` и `resolution` у подтверждений, а также
`pending_color` у последнего незавершённого ответа (включая уточнение). Это позволяет
восстановить кнопки и состояние после перезагрузки; предложение и его цвет
сохраняются в существующих sessions/metadata, включая перезапуск сервера.
Явный `new_event_color: null` сбрасывает индивидуальный цвет; пропуск поля
сохраняет цвет незавершённого предложения. Старые клиенты без флага сохраняют
прежнее поведение. Общие Event/ParsedCommand-контракты не изменены.
Полное описание и ограничения — в `web/CONTEXT_UI.md`.

## Цель

Подключить все элементы интерфейса задач, напоминаний, календаря и ассистента
к реальным данным. Сейчас часть возможностей недоступна из-за отсутствующих
полей и серверной логики. Frontend не имитирует приоритеты, пространства,
облачную синхронизацию или доставку уведомлений.

## Что уже есть и нужно сохранить

| Метод | Текущее поведение |
| --- | --- |
| `POST /api/message` | Текстовая команда, создание, поиск, уточнения и подтверждения; повтор по `request_id` |
| `POST /api/events` | Структурированное создание из формы, тот же core и проверки конфликтов |
| `GET /api/colors` | Цвета типов и индивидуальные цвета записей |
| `PATCH /api/colors/defaults/{event_type}` | Цвет типа либо сброс к системному |
| `PATCH /api/events/{id}/color` | Цвет отдельной записи либо наследование |
| `GET /api/events` | Записи; фильтры `from`, `to`, `type`, `status`, `include_undated` |
| `GET /api/search` | Поиск по `q`, ограничение `limit` |
| `PATCH /api/events/{id}` | Изменение `title`, `date`, `time`, `status` |
| `DELETE /api/events/{id}` | Мягкое удаление |
| `GET /api/history` | История по `session_id`, ограничение `limit` |
| `POST /api/speech` | Распознавание PCM-аудио |
| `GET /api/health` | Проверка доступности приложения |

Существующие типы записей: `task`, `meeting`, `reminder`.
Статусы: `planned`, `done`. Задачи уже являются записями `/events`:
параллельный дублирующий CRUD `/tasks` не требуется.

В текущем запущенном контракте нет описания, приоритета, пространства, календаря,
даты завершения и настройки доставки напоминания. Время хранится без timezone.
В присланной ER-схеме описание и временная модель уже предусмотрены — см. сверку выше.
Авторизации нет: сессия разделяет диалог, но записи находятся в общей базе.

## Приоритет 1. Полноценные задачи и редактор

### Методы

| Изменение | Зачем frontend |
| --- | --- |
| Расширить уже реализованный `POST /api/events` | Добавить согласованные описание, приоритет, пространство и календарную связь |
| Добавить `GET /api/events/{id}` | Актуальные данные при открытии из поиска, уведомления или ссылки |
| Расширить `PATCH /api/events/{id}` | Сохранение всех полей редактора |
| Расширить `GET /api/events` | Фильтры, серверная сортировка, пагинация и счётчики групп |

### Необходимые данные

| Поле / возможность | Требование |
| --- | --- |
| `description` | Описание; отдельно от названия |
| `priority` | Четыре уровня: срочная, важная, средняя, низкая; значения enum согласовать |
| `status` | Добавить состояние «В процессе», сохранив существующие статусы |
| `completed_at` | Реальное время завершения, устанавливаемое сервером |
| `workspace_id` | Принадлежность пространству |
| `version` или ETag | Проверка, что редактируется актуальная версия |
| Дедлайн | Дата/время срока задачи с однозначной временной семантикой |
| Календарное размещение | Необязательные календарь и интервал размещения задачи |
| Время встречи | Начало и окончание либо начало и длительность; возможность редактирования |

В PATCH нужно определить различие между отсутствующим полем («не менять»)
и `null` («очистить»). Обязательные поля нельзя очищать невалидным запросом.
При возврате завершённой задачи в открытые нужно определить поведение
`completed_at`; рекомендуемый вариант — очистить его, историю изменений хранить отдельно.

Создание должно поддерживать идемпотентность: повтор после потери ответа
не создаёт вторую запись. Сохранение возвращает полную актуальную запись.
При конфликте версий сервер возвращает согласованную ошибку конфликта,
а не молча перезаписывает чужие изменения.

Для списка нужны фильтры по пространству, календарю, статусу, типу и приоритету;
сортировка по сроку/приоритету; `cursor`/`limit` либо согласованная альтернатива.
Счётчики групп должны учитывать весь набор по фильтру, а не только текущую страницу.
Поиск должен учитывать пространство и возвращать достаточно данных для открытия записи.

## Приоритет 1. Пространства

Нужно сделать работающим селектор пространства в верхней панели.

| Предлагаемый метод | Назначение |
| --- | --- |
| `GET /api/workspaces` | Доступные пространства, их ID и названия |
| `POST /api/workspaces` | Создание пространства, если это доступно пользователю |
| `PATCH /api/workspaces/{id}` | Переименование / архивирование |
| `DELETE /api/workspaces/{id}` | Только после определения судьбы связанных данных |

Записи, поиск, счётчики и контекст ассистента должны быть ограничены выбранным
пространством. Сервер проверяет доступ, а не полагается на фильтрацию в браузере.
Нужно определить пространство по умолчанию и миграцию существующих записей в него.
Удаление пространства не должно неявно удалять пользовательские данные.

## Приоритет 1. Настоящие напоминания

Сейчас `type=reminder` — обычная запись с датой и временем. Она не отправляет
уведомление и не является настройкой напоминания у задачи или встречи.

| Предлагаемый метод | Назначение |
| --- | --- |
| `GET /api/events/{id}/reminders` | Настройки напоминаний записи |
| `POST /api/events/{id}/reminders` | Добавление напоминания, например за 10 минут |
| `PATCH /api/reminders/{id}` | Включение, отключение, изменение времени и канала |
| `DELETE /api/reminders/{id}` | Удаление настройки и отмена ожидающей доставки |

Нужные данные: ID, связанная запись, `enabled`, смещение до события или абсолютное
время отправки, timezone, канал, фактическое состояние доставки и время доставки.
Названия полей и перечисления согласовать. Нужно определить, какое время является
базовым для относительного напоминания: дедлайн, начало встречи или иной момент.

Самостоятельные напоминания из текущего `/events` необходимо сохранить.
Способ их связи с новым механизмом доставки нужно определить без создания дублей.

**Нужна серверная логика, а не только endpoints:**

- Фоновый планировщик, который работает при закрытой странице.
- Надёжная обработка ожидающих отправок после перезапуска сервера.
- Пересчёт времени отправки при переносе связанного события.
- Отмена при отключении, удалении и согласованная политика при завершении задачи.
- Повторы при временных ошибках и защита от повторной доставки.
- Политика для просроченных напоминаний и смены часового пояса.
- Статусы, которые различают запланированную отправку, ошибку и подтверждённую доставку.

Для центра уведомлений и браузерного push предлагаются:

- `GET /api/notifications` — список, пагинация, число непрочитанных.
- `PATCH /api/notifications/{id}` — прочтение / закрытие.
- `POST /api/push-subscriptions` — регистрация подписки.
- `DELETE /api/push-subscriptions/{id}` — отзыв подписки.

Нужно заранее выбрать канал доставки для MVP. Журнал уведомлений сам по себе
не обеспечивает доставку при закрытом браузере.

## Приоритет 1. Время и часовые пояса

Нельзя использовать одно поле для всех временных значений. Необходимо различать:

1. Дедлайн задачи.
2. Начало/окончание встречи.
3. Интервал задачи в календаре.
4. Время отправки напоминания.

Пример: задача размещена в календаре с 13:30 до 14:00, дедлайн — 18:00,
напоминание — в 17:50. Это разные значения.

Нужны однозначные моменты времени, например ISO 8601 со смещением/UTC,
и сохранённая IANA timezone, например `Europe/Moscow`. Для задач без времени
нужна отдельная семантика даты, без выдуманного дедлайна в полночь.

Нужно согласовать миграцию старых naive `date`/`time`: в какой зоне они были
заданы и как их интерпретировать. Просто дописать `Z` к старым значениям нельзя.
Часы backend и тесты должны продолжать использовать `Clock`/`FixedClock`.

Часовой пояс можно получать через `GET /api/me` при наличии пользователей
либо через настройки локального приложения, если оно остаётся однопользовательским.

## Приоритет 2. Календарь и профиль

Для внутреннего календаря нужны:

- `GET /api/calendars` — ID, название, доступность редактирования, при необходимости цвет.
- Связь записи с календарём и необязательным интервалом размещения.
- Фильтрация записей по календарю и периоду через существующий `GET /api/events`.
- Создание/изменение/архивирование календарей — если такое управление входит в продукт.

Для нескольких пользователей нужны авторизация, серверная сессия, проверка
владельца/прав на каждую сущность и `GET, PATCH /api/me` для профиля и timezone.
Точные методы входа/выхода зависят от выбранного способа авторизации.
Текущий `session_id` диалога не должен использоваться как доказательство доступа к данным.

## Приоритет 2. Темы диалога и предложения ассистента

| Изменение | Назначение |
| --- | --- |
| `GET, POST /api/conversations` | Список тем и создание разговора |
| `PATCH, DELETE /api/conversations/{id}` | Переименование и архивирование/удаление |
| Расширить `POST /api/message` | Передавать явные ID разговора и пространства |
| Расширить `GET /api/history` | Пагинация, структурированные карточки и ожидаемые действия |

Темы переписки и рабочие пространства — разные сущности, их связь нужно определить явно.
Для восстановления интерфейса после перезагрузки истории недостаточно текста:
нужны ссылки на записи, типы карточек и актуальное состояние доступных действий.
Необходимо определить, где показывается исторический снимок, а где актуальная запись.

Если требуется редактируемая карточка перед любым действием AI, нужен контракт
предложения с ID, типом действия, полями, состоянием и сроком действия. Например:

- `PATCH /api/assistant/actions/{id}` — изменить предложение до исполнения.
- `POST /api/assistant/actions/{id}/confirm` — исполнить подтверждённое действие один раз.
- `POST /api/assistant/actions/{id}/cancel` — отменить предложение.

Для существующего подтверждения конфликтов уже работает `POST /api/message`.
Новый механизм нужен только для общего workflow предложений; он не должен
создавать второй независимый путь повторного исполнения той же операции.

## Приоритет 2–3. Обновления и реальные интеграции

Для своевременного обновления вкладок/устройств предлагается `GET /api/stream`
через SSE: ID события для восстановления, тип изменения, ID/версия сущности,
ограничение по правам и пространству. Альтернатива — согласованный polling
с механизмом поиска изменений. Нужен один выбранный подход.

Для облака и внешних календарей, если они входят в продукт:

- `GET /api/integrations` — подключения и фактическое состояние.
- Методы подключения, callback и отключения выбранного провайдера.
- `GET /api/sync/status` — ожидающие операции, ошибки, последняя подтверждённая синхронизация.
- `POST /api/sync/retry` — повтор неудачной синхронизации, если доступен пользователю.

Нужны реальная интеграция, обработка конфликтов и фоновые повторы.
Ответ `/api/health` и успешное сохранение в SQLite не означают синхронизацию с облаком.

## Приоритет 3. Файлы и «Поделиться»

Реализовывать после подтверждения, что эти функции включаются в продукт:

| Предлагаемый метод | Назначение |
| --- | --- |
| `POST /api/attachments` | Загрузка с ограничениями размера и формата |
| `GET, DELETE /api/attachments/{id}` | Получение/удаление с проверкой доступа |
| Связь вложения с записью/сообщением | Отображение и жизненный цикл файла |
| `POST /api/events/{id}/shares` | Создание доступа с определёнными правами и сроком действия |
| `DELETE /api/shares/{id}` | Отзыв доступа |

Нужно определить хранилище файлов, доступные права, сроки хранения и поведение
при удалении связанной сущности. Ссылка «Поделиться» не должна открывать всю общую базу.

## Общие требования и совместимость

- Зафиксировать согласованные DTO, enum, допустимые `null`, ошибки и примеры в OpenAPI.
- Сохранить существующие методы, мягкое удаление и идемпотентность `request_id`.
- Не менять форму текущих ответов списка/поиска без совместимой версии API.
- Новые необязательные поля можно добавлять согласованно. **Новые значения enum
  требуют одновременной поддержки frontend:** сейчас валидатор принимает только
  `planned`/`done`. Раннее появление `in_progress` приведёт к отклонению списка.
- Определить стабильную сортировку и полные счётчики при пагинации.
- Изолировать данные по владельцу и пространству на сервере.
- Не молча перезаписывать изменения при конфликте версий.
- Сохранить существующий архив и пользовательскую базу; для миграций предусмотреть резервирование.
- Все тесты и миграционные проверки выполнять на временной базе, без внешнего LLM.

## Критерии приёмки первой поставки

1. Из формы создаётся задача с названием, описанием, приоритетом, сроком и пространством;
   повтор запроса не создаёт дубль.
2. Задача переходит между «Созданные», «В процессе», «Завершённые»;
   сервер возвращает корректное время завершения.
3. Изменения одинаково видны в списке, редакторе, «Мой день», календаре и поиске.
4. При смене пространства данные и поиск не смешиваются с другим пространством.
5. К задаче/встрече добавляется напоминание за заданное время. Перенос, отключение
   и удаление корректно меняют ожидающую доставку.
6. Напоминание обрабатывается при закрытой странице и после перезапуска сервера;
   ошибки и повторы не создают повторную доставку одной операции.
7. Время корректно передаётся и отображается при разных timezone клиента и сервера.
8. Два клиента не могут незаметно перезаписать одну версию записи.
9. Старые данные и действующие сценарии диалога продолжают работать.
