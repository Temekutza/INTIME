# Aivritm: интерфейс и проверка реализации

Актуальный этап: единые Select/DatePicker/TimePicker/Popover и модальные окна,
доработанная панель ассистента и обязательное подтверждение создания через чат.
Результат: **476 pytest / 15 Node / 58 E2E** полного прогона; затем прошли
6 целевых E2E, включая новый сценарий восстановления цвета при уточнении.
Typecheck и lint проходят.
Подробный отчёт, API и проверки — в [CONTEXT_UI.md](CONTEXT_UI.md).
Предыдущий этап (типографика, цвета, форма и сворачивание «Моего дня») —
в [FIXES.md](FIXES.md); его результат составлял 470 / 15 / 46 тестов.

Обновление: реализована серверная персонализация цветов типов и отдельных записей.
Актуальные методы, поведение наследования, результаты проверок и ограничения —
в [COLORS.md](COLORS.md). Приведённые ниже 440/10/23 теста относятся к первоначальному
этапу интерфейса; после добавления цветов итог составляет 454/15/35.

## 1. Что обнаружено

До изменений frontend представлял собой один экран диалога в `web/index.html`,
`web/app.js`, `web/styles.css`. FastAPI отдаёт страницу по `/`, файлы по `/static/`.
Backend — Python 3.14, FastAPI 0.159.1, SQLite. Контракт — `ritm/contracts.py` v1.3.
React, Next.js, маршрутизатора frontend, сборщика, WebSocket, SSE и polling нет.
Изначальное рабочее дерево Git было чистым.

Авторизации и профилей нет. `ritm.session_id` в localStorage разделяет диалоги,
а записи доступны в общей базе. Это не механизм разграничения доступа.
Запросы идут на относительные URL того же сервера; настройки CORS не менялись.
Конфигурация backend, секреты, рабочая база и исходный архив не изменялись.

## 2. Архитектура

Сохранён один frontend без обязательной сборки и новых runtime-зависимостей.
Переход на React/Next.js потребовал бы отдельной миграции существующих голоса,
истории, подтверждений и запуска Python. В этой задаче применён приоритет
сохранения работающей архитектуры из исходного запроса.

| Модуль | Ответственность |
| --- | --- |
| `dashboard.js` | Компоновка, навигация, поиск, часы и UI-состояние |
| `lib/types.d.ts` | DTO существующего контракта, допустимые PATCH-поля |
| `lib/api.js` | HTTP, отмена, таймауты, ошибки и проверка ответов |
| `lib/store.js` | Общая подтверждённая коллекция записей и PATCH |
| `lib/model.js` | Даты, сортировка, группировка и валидация |
| `lib/views.js` | Задачи, напоминания, календарь, «Мой день» |
| `lib/editor.js` | Черновик, проверка и явное сохранение записи |
| `lib/ui.js` | DOM-элементы и единый набор контурных иконок |
| `app.js` | Существующие диалог, голос, история, повторы и удаление |

Оба контроллера используют один экземпляр EventStore и общий PATCH-клиент.
Изменения через диалог вызывают обновление коллекции. Ответ старого GET
не заменяет данные после более нового изменения. Незавершённый PATCH одной
записи блокирует повторный PATCH этой записи. Успех показывается после ответа
сервера. Черновик редактора отделён от коллекции и сохраняется при обновлении.
Прочие вкладки обновляют данные по фокусу окна; потоковой синхронизации нет.

Новые модули проверяются TypeScript в режиме strict/checkJs по JSDoc и `.d.ts`.
Существующий голосовой контроллер остаётся JavaScript: на него распространяется
ESLint и регрессионные тесты, но не строгая проверка типов.

Решения сверены с документацией: [CSS minmax](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/minmax),
[проверка JavaScript в TypeScript](https://www.typescriptlang.org/docs/handbook/type-checking-javascript-files.html),
[ожидания Playwright](https://playwright.dev/docs/test-assertions).

## 3. Реализованный функционал

- Три колонки, вкладки, аналоговые и цифровые часы, текущие встречи и задачи.
- Группы реальных статусов `planned`/`done`, фильтр, сортировка и сворачивание групп.
- Редактор названия, даты, времени и статуса; явное сохранение и ошибки валидации.
- Завершение и возврат в открытые; согласованное состояние списка, редактора,
  боковой панели, календаря и существующих карточек диалога.
- Календарь по дням с задачами, встречами и отдельными напоминаниями.
- Напоминания по датам, сортировка, относительное время и редактирование.
- Поиск сервером, состояния загрузки/пустой выдачи/ошибки, открытие результата.
- Ассистент сворачивается с освобождением колонки; история и черновик остаются.
- Создание через существующий диалог: кнопки подставляют начало команды,
  пользователь дополняет и отправляет её. Конфликты подтверждаются пользователем.
- Повтор после потери ответа использует прежний request_id и не создаёт дубль.
- Клавиатура, Enter/Shift+Enter, labels, focus, aria-live, подтверждение удаления
  и предупреждение о закрытии несохранённого редактора.

## 4. API Integration

| Endpoint | Использование |
| --- | --- |
| `GET /api/events` | Общая коллекция, все представления и повтор загрузки |
| `GET /api/search?q=…&limit=20` | Глобальный поиск с отменой устаревших результатов |
| `PATCH /api/events/{id}` | Название, дата, время, `planned`/`done` |
| `POST /api/message` | Создание, запросы и явные подтверждения через диалог |
| `POST /api/events` | Создание из формы через ту же core-политику, с подтверждением конфликтов |
| `GET /api/history` | История сессии; поздний ответ старой сессии отбрасывается |
| `DELETE /api/events/{id}` | Удаление после подтверждения |
| `POST /api/speech` | Сохранённое локальное распознавание речи |
| `GET /api/health` | Готовность изолированного backend в браузерных тестах |

API не поддерживает пагинацию списка: dashboard получает полную коллекцию.
Поиск не загружает коллекцию дополнительно, а использует собственный endpoint.
Для существенно больших объёмов потребуется согласовать пагинацию backend.

## 5. Вёрстка

Светлая палитра, фиолетовый акцент, компактные элементы и спокойные поверхности
сверены с двумя изображениями пользователя. Красные аннотации не воспроизводились.
Поскольку в модели нет приоритета, разноцветные карточки не выдаются за реальные
уровни приоритета. Завершённые записи отмечены зелёной поверхностью и checkbox.
Это визуальная сверка композиции, а не автоматическое пиксельное сравнение.

Grid использует `minmax(0, 1fr)` и минимальные размеры внутренних областей.
Левая панель, список, редактор и диалог прокручиваются независимо. Поле ввода
остаётся внизу AI-панели. При её закрытии grid пересчитывает число колонок.
Для ширин ниже 1180 CSS px предусмотрена горизонтальная прокрутка рабочего
пространства; мобильной перестройки нет.

Проверены 1280×800, 1343×868, 1366×768, 1440×900, 1536×985, 1920×1080;
увеличенные панели; настоящий масштаб вкладки Chromium 125%; длинные заголовки,
200 записей и 80 сообщений. Проверки геометрии выявляют горизонтальный overflow
и пересечения колонок, редактора и поля ввода.

## 9. Оставшиеся проблемы и решения для Claude

Контракт не содержит описания, приоритета, статуса «в процессе», пространств,
профиля, календарей, вложений и связи напоминания с задачей. Такие поля не выдуманы.
Селектор пространства, уведомления и вложения явно недоступны. Настоящих push
и облачной синхронизации нет; индикатор показывает состояние запросов к серверу.
Дата завершения отсутствует: sidebar честно показывает время обновления записи.

Сервер хранит naive date/time без часового пояса. UI использует локальную зону
браузера; время записей должно совпадать с локальным временем сервера. Часовой
пояс записи и конвертацию между зонами нельзя корректно добавить без контракта.
Для редактора нет версии записи/ETag: сохранение не обеспечивает разрешение
конфликтов между несколькими независимыми пользователями. Авторизация также
остаётся за пределами существующего прототипа.

Claude необходимо согласовать расширения контракта для перечисленных функций,
timezone, оптимистической блокировки и пагинации. Миграция на React/Next.js,
если обязательна, требует отдельного решения о сборке, раздаче и переносе голоса.
Применимую WCAG-семантику поддержали, но полноценный аудит соответствия WCAG AA
и проверки Firefox/WebKit не выполнялись.

### 9.1. Какие API нужны для полной реализации

Ниже — предложение для согласования с Claude, а не существующие endpoints.
Названия маршрутов предварительные. Новые возможности следует добавлять
совместимо с текущими потребителями; общие типы и миграции согласуются отдельно.
Отдельный дублирующий CRUD `/tasks` не требуется: задачи уже являются `/events`.

**Первый этап — поля и операции, необходимые для экранов из задания.**

| Метод | Для чего нужен |
| --- | --- |
| `POST /api/events` | Структурированное создание из формы, без разбора русской фразы; идемпотентность по ключу запроса |
| `GET /api/events/{id}` | Открытие актуальной записи из поиска, уведомления или ссылки |
| Расширить `PATCH /api/events/{id}` | Описание, приоритет, статус «в процессе», пространство, календарная связь; проверка версии записи |
| Расширить `GET /api/events` | Фильтры по пространству/календарю/приоритету, сортировка, cursor/limit, полные счётчики для групп |
| `GET, POST /api/workspaces` | Список и создание пространств |
| `PATCH, DELETE /api/workspaces/{id}` | Переименование и согласованное архивирование/удаление пространства |
| `GET, POST /api/events/{id}/reminders` | Получение и создание напоминаний, связанных с записью |
| `PATCH, DELETE /api/reminders/{id}` | Включение, отключение, перенос и удаление напоминания |
| `GET, POST /api/calendars` | Список и создание внутренних календарей |
| `PATCH, DELETE /api/calendars/{id}` | Настройки и жизненный цикл календаря, если пользователь должен ими управлять |
| `GET, PATCH /api/me` | Профиль, отображаемое имя, IANA timezone, локаль |

Для редактируемой записи нужны `description`, `priority`, `workspace_id`,
`completed_at`, `version` и согласованный статус `in_progress`. `completed_at`
заполняет сервер при завершении; `updated_at` его не заменяет.

Время необходимо моделировать раздельно: дедлайн задачи, начало/окончание встречи,
необязательный интервал задачи в календаре и момент отправки напоминания.
Например, задача может занимать 13:30–14:00 в календаре и иметь дедлайн 18:00.
Текущие naive `date`/`time` требуют согласованной миграции к однозначным моментам
времени с сохранением IANA timezone. Нельзя просто дописать `Z` к старым значениям.
Напоминание должно содержать связь с записью, включённость, смещение до события
либо самостоятельный момент отправки, канал и фактический статус доставки.

**Второй этап — полноценные диалоги, доставка и обновления.**

| Метод | Для чего нужен |
| --- | --- |
| `GET, POST /api/conversations` | Список тем диалогов и создание нового разговора |
| `PATCH, DELETE /api/conversations/{id}` | Переименование и удаление/архивирование разговора |
| Расширить `POST /api/message` и `GET /api/history` | Явная связь с разговором и пространством, пагинация истории, структурированные карточки и ожидаемые действия |
| `PATCH /api/assistant/actions/{id}` | Редактирование предложения ассистента до исполнения, если нужен общий preview-workflow |
| `POST /api/assistant/actions/{id}/confirm` | Однократное исполнение конкретного проверенного предложения |
| `POST /api/assistant/actions/{id}/cancel` | Явный отказ от предложения |
| `GET /api/notifications` | Список уведомлений с пагинацией и числом непрочитанных |
| `PATCH /api/notifications/{id}` | Отметка прочтения/закрытия уведомления |
| `POST /api/push-subscriptions`, `DELETE /api/push-subscriptions/{id}` | Регистрация и отзыв браузерной push-подписки |
| `GET /api/stream` (SSE) | Изменения записей и уведомления между вкладками/устройствами; восстановление по ID события |

Темы разговоров и рабочие пространства — разные сущности. Сервер должен явно
проверять принадлежность сообщений и записей пользователю и пространству.
Для текущего подтверждения конфликтов уже достаточно `POST /api/message`;
маршруты `assistant/actions` нужны, только если вводится единый редактируемый
предпросмотр перед любым изменением. Они не должны создавать второй путь
повторного исполнения того же действия.

**Третий этап — возможности, зависящие от выбранных интеграций.**

| Метод | Для чего нужен |
| --- | --- |
| Методы входа/выхода и получения сессии | Пользовательская авторизация; конкретные маршруты зависят от выбранного способа входа |
| `GET /api/integrations` | Подключённые внешние календари/облачные сервисы и их состояние |
| Методы подключения, callback и отключения интеграции | Авторизация конкретного провайдера; состав зависит от Google Calendar, CalDAV и других выбранных систем |
| `GET /api/sync/status`, `POST /api/sync/retry` | Подтверждённое состояние реальной синхронизации и повтор неудачной операции |
| `POST /api/attachments` | Загрузка файлов с реальными ограничениями формата и размера |
| `GET, DELETE /api/attachments/{id}` | Получение/удаление доступного пользователю вложения; привязка к сообщению или записи |
| `POST /api/events/{id}/shares`, `DELETE /api/shares/{id}` | Создание и отзыв ссылки с определёнными правами доступа, если включается «Поделиться» |

Самих HTTP-методов недостаточно для доставки и облака: нужны фоновый планировщик,
очередь доставки с повторами и защитой от дублей, обработка изменения/удаления
напоминаний и реальная интеграция с провайдером. До их появления состояние
«Всё синхронизировано» и статус «доставлено» показывать нельзя.

Общие условия контрактов: идемпотентность создания/подтверждения, ETag/If-Match
или эквивалентная проверка версии с ответом о конфликте, однозначные timezone,
серверная валидация, согласованные ошибки, пагинация и проверка прав на каждую
сущность. При удалении пространства/календаря необходимо определить судьбу
связанных записей. Для MVP в первую очередь нужны первый этап и настоящая
доставка напоминаний; внешнее облако, файлы и общий доступ можно включать отдельно.

## 10. Запуск на Windows

Обычный запуск из корня проекта, без Node и без сборки:

```powershell
uv venv --python 3.14 .venv
uv pip install --python .venv\Scripts\python.exe -r requirements-dev.txt
.venv\Scripts\python -m ritm
```

Интерфейс: `http://127.0.0.1:8000`. Это обычный запуск с рабочей конфигурацией;
для тестов использовать следующие команды, которые не открывают рабочую базу:

```powershell
.venv\Scripts\python -m pytest -q
npm --prefix web ci
npm --prefix web run typecheck
npm --prefix web run lint
npm --prefix web test
$env:AIVRITM_TEST_PYTHON = (Resolve-Path .venv\Scripts\python.exe).Path
npm --prefix web exec -- playwright install chromium
npm --prefix web run test:e2e
```

Для установленного отдельно Chromium можно передать полный путь к `chrome.exe`
через `AIVRITM_BROWSER_PATH`. В текущей проверке использован
`%LOCALAPPDATA%\ms-playwright\chromium-1248\chrome-win64\chrome.exe`, а Python взят
из `%TEMP%\aivritm-frontend-venv\Scripts\python.exe`.
`AIVRITM_TEST_PORT` меняет тестовый порт; `AIVRITM_TEST_ARTIFACTS` — папку отчётов.
По умолчанию отчёты, скриншоты, трассы, временные базы и профиль тестового
браузера остаются вне репозитория.
