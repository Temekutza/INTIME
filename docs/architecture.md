# Архитектура и технологии

InTime — один Compose-стек. Браузер открывает интерфейс, nginx отдаёт статику и проксирует `/api` в backend. Backend хранит записи в своём PostgreSQL и для понимания фразы вызывает локальную модель через шлюз.

```text
браузер
   |
   v
nginx :3010          статический интерфейс
   |
   v
FastAPI :8010        /api и /api/v1
   |            \
   v             v
PostgreSQL 16    LiteLLM :4000
:5435                 |
                      v
                 Ollama :11435
                      |
                      v
                 Qwen3-32B на RTX 4090
```

Интерфейс — обычный JavaScript, ES-модули, без React и без сборки. Его отдаёт nginx 1.27. Календарь (день / неделя / месяц / год / список), задачи, напоминания, «Мой день», чат и форма создания ходят в один контракт `/api`: события, пространства, цвета, история, сообщение ассистенту и речь.

Выбранное рабочее пространство действует на списки, поиск, историю чата и создание записей. Типы: задача, встреча, напоминание. В интерфейсе статусы `planned` и `done`. Название обязательно; у задачи дата необязательна; у встречи и напоминания нужны дата и время; длительность встречи 1–1440 минут.

Backend — Python 3.12, FastAPI, Pydantic и асинхронный SQLAlchemy. Рядом второй контракт `/api/v1`: регистрация, cookie-сессия и прямой доступ к записям. Оба слоя смотрят в одну базу. Схема — `backend/sql/001_init.sql` … `004_workspaces.sql`, накатывается только при первом создании тома Postgres.

Без cookie слой `/api` работает от демо-пользователя `COMPAT_USER_LOGIN` (обычно `anna`). Создание и изменение через чат ждут подтверждения.

Ассистент не вызывает модель напрямую. Запрос идёт в LiteLLM (`ghcr.io/berriai/litellm:main-v1.83.14-stable.patch.3`), дальше в системную Ollama. Снаружи модель называется `qwen3-32b`. Это локальный алиас `intime-qwen3-32b` поверх весов Qwen3-32B Q5_K_M: тот же файл, но шаблон не оставляет ответ внутри блока рассуждений. Ключи приложений, лимиты и учёт токенов хранит отдельный PostgreSQL шлюза, не база планировщика. Master key наружу не отдаётся. Пустой `LLM_API_KEY` выключает ассистента.

Ollama слушает только `127.0.0.1:11435`, поэтому контейнер LiteLLM работает в сети хоста. Backend из обычной Docker-сети до этого адреса не доходит. Рядом стоит проброс `litellm-docker`: он принимает соединение на адресе docker-моста и передаёт его на `127.0.0.1:4000`.

Распознавание речи вынесено отдельно: GigaAM на порту хоста `9000`, nginx проксирует `/stt/`. Синтез речи в коде есть, в текущей конфигурации не подключён (`TTS_API_KEY` пустой). Публичный вход один: существующий Caddy на порту `8088` отдаёт сайт, API и Swagger с того же HTTPS-имени. Порты приложения в Compose слушают `127.0.0.1`. База и шлюз модели снаружи не опубликованы.
